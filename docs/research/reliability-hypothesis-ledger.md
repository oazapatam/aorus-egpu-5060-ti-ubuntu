### H14 — First rm_init_adapter on cold-cold-boot fails due to a transient bus state during initial GSP boot (root cause of H13's WPR2-stuck cycle)

| Field | Value |
|---|---|
| Status | **MULTI-CAUSE CONFIRMED 2026-05-07 14:54** — H14's "first rm_init_adapter failure" has at least TWO independent triggers: (1) IOMMU rejection (eliminated by `iommu=off`) and (2) PCIe link transient during GSP boot ([H16](#h16), independent of IOMMU). See [`docs/iommu-gsp-lockdown-analysis.md`](./iommu-gsp-lockdown-analysis.md) for the comprehensive analysis. |
| Discovered | 2026-05-06 15:47:34 — diagnostic patch 0018 captured `PMC_BOOT_0=0x00000000` at `post-rmInit-FAIL` site, vs `0x1b2000a1` at all other read sites in the same boot |
| Evidence FOR | At post-rmInit-FAIL site of the FIRST failed attempt: PMC_BOOT_0 reads 0 (not 0xFFFFFFFF — bus is electrically alive but the register is literally zero). At every subsequent read site (including post-rmInit-FAIL of retries): PMC_BOOT_0 = 0x1b2000a1 (normal value). The bus enters and exits a transient state during the first GSP boot attempt. |
| **Evidence FOR (refined 2026-05-06 16:24)** | **524 DMAR/IOMMU fault entries during the Commit 3 recovery storm.** Every `rm_init_adapter` attempt produces faults like `DMAR: [DMA Write NO_PASID] Request device [04:00.0] fault addr 0xXXXXXXXX [fault reason 0x71] SM: Present bit in first-level paging entry is clear`. Pattern: GSP firmware tries to DMA. IOMMU has no first-level paging entry for the address. IOMMU rejects. GSP boot fails. WPR2 left set. The PMC_BOOT_0=0 transient observed earlier is consistent with the GPU/GSP being in a stalled state during the failed DMA. |
| Evidence AGAINST | None observed; need n≥3 cold-cold-boots with diagnostic to confirm IOMMU pattern. |
| Mechanism (hypothesis, refined) | Initial GSP boot loads firmware, attempts DMA setup for its secure regions and runtime structures. The IOMMU (Intel VT-d, force-enabled per platform opt-in per dmesg `Intel-IOMMU force enabled due to platform opt in`) doesn't have those addresses mapped — either because: (a) NVIDIA driver isn't pre-registering them via `iommu_dma_map_*` before GSP boot tries to use them; (b) the IOMMU is in strict mode and the windows of validity are mismatched with GSP's expectations; (c) there's a race condition between IOMMU mapping setup and GSP firmware activation. IOMMU rejects → GSP DMA fails → GSP self-bootstrap fails → leaves WPR2 set in hardware → subsequent rm_init_adapter retries see "WPR2 already up" and refuse to retry. |
| **Mechanism (CRYSTAL CLEAR 2026-05-06 16:50)** | **GSP firmware enters LOCKDOWN mode** in response to DMA rejection. Direct evidence from kernel log RPC event history: GSP firmware sends `GSP_LOCKDOWN_NOTICE` (function 4124) repeatedly to host driver instead of `GSP_INIT_DONE` (function 4097). | Instrumento | [`tools/egpu-oc-edge`](../../tools/egpu-oc-edge). Fuente: <https://forums.developer.nvidia.com/t/silent-cuda-compute-corruption-on-rtx-pro-6000-blackwell/381759>. Ninguna ventana de minutos descarta esa cola. Lo que mide esta hipótesis es el **borde grueso** —dónde falla de forma detectable en minutos— y por eso el resultado se enuncia siempre con su cobertura ("cero errores en N iteraciones sobre T segundos, n=K") y nunca como "este offset es seguro". |
| Trampa que el instrumento tiene que esquivar (y por la que se mide el reloj) | Un paso que **pasa sin mover el reloj** no es margen conseguido: es un offset que el driver se ha comido. Sin medir el efecto, un "+6000 MHz de memoria estable" sería el mismo engaño por el que se retiró el perfil `performance` (que escribía valores que la tarjeta ya tenía). Cada paso se clasifica además por efecto: `nucleo`, `memoria`, `ambos` o `ninguno`. |
| Confusor que hay que separar de un fallo de reloj | Un `Xid 79` / "fallen off the bus" **no es** culpa del offset: es la firma de [H23](#h23) (se cae el dispositivo Thunderbolt entero). El instrumento lo detecta en el journal del tramo y **aborta** en vez de apuntar un fallo que no es del reloj; el veredicto formal lo da `aorus-egpu-health`. Simétricamente, un paso que pasa los bits pero deja líneas NVRM en el journal se marca **inválido**, no "pasa": la evidencia no está limpia. |
| Gates que no se negocian durante la medición | Gate R4 dentro del helper NVML (device 0x2d04; la interna 0x2c39 aborta). Gate de enlace por **capacidad negociada** (`pcie.link.gen.max`), revalidado **antes de cada paso** y no solo al arrancar, porque H23 dice que el túnel se cae en reposo y escribir justo después de una caída es lo que congeló el host. **No hay `--force`**. Offsets a 0 al salir —final normal, excepción, Ctrl-C o SIGTERM— y la vuelta **confirmada releyendo**. El offset se relee tras cada paso: si cambió a mitad (un reset de GPU los borra), el paso es inválido, porque habría medido la tarjeta sin el offset puesto. Si el hijo no vuelve, se aborta **sin reintentar**. |
| Resolution test | El barrido completo de `tools/egpu-oc-edge` con n=3 de 90 s en el candidato de cada dominio. Resuelve con: un borde confirmado en el núcleo y otro en la memoria, cada uno con efecto medido en el reloj (`efecto != ninguno`), más la combinación de los dos valores recomendados confirmada aparte. Si la escalera llega al techo de la ventana NVML sin un solo fallo, el límite medido es **la ventana, no el silicio**, y eso hay que decirlo así. |
| If supported | Hay un número con el que discutir perfiles, y el gate de verificación de `aorus-egpu-oc` deja de ser teórico: existe un offset que lo pasa. **No** implica que se entregue un perfil con offsets positivos: para una carga de IA sin ECC esa decisión sigue necesitando su propia justificación, y la dirección segura del tuning en esta máquina es hacia abajo. |
| If rejected | Si cualquier offset positivo medible corrompe bits, o si los offsets pasan sin mover el reloj, la conclusión de `docs/overclock.md` se mantiene con una base mucho más firme que antes: en esta tarjeta el overclock no existe, y ahora medido en vez de supuesto. |
| Layer | L4 (userspace: NVML VF offsets + el verificador numérico). Ninguna palanca de kernel ni de firmware interviene. |
| Cross-references | [`docs/overclock.md`](../overclock.md) (capacidades medidas de la tarjeta, perfiles y el riesgo de no tener ECC); [`docs/research/lever-catalog.md`](./lever-catalog.md); [H23](#h23) (pérdida del dispositivo TB: el confusor que hay que separar); [`docs/freeze-forensics.md`](../freeze-forensics.md) (por qué la medición va envuelta en `aorus-egpu-probe`) |

| Mecanismo — paso 2: la escritura ocurre con IRQs deshabilitadas | `uvm_parent_gpu_replayable_faults_isr_lock()` (`uvm_gpu_isr.c`) hace `uvm_spin_lock_irqsave(&parent_gpu->isr.interrupts_lock)` y **dentro** de esa sección llama a `uvm_parent_gpu_replayable_faults_intr_disable()`, que a su vez invoca `parent_gpu->fault_buffer_hal->disable_replayable_faults(parent_gpu)`. | Mecanismo — por qué la única guarda existente no cubre este caso | `UVM_GPU_WRITE_ONCE` (`uvm_global.h:252`) es `UVM_ASSERT(!uvm_global_is_suspended())` + `WRITE_ONCE`. Su comentario lo dice literalmente: *"Use these … when accessing GPU resources in BAR0/BAR1 to detect cases in which GPUs are accessed when UVM is suspended."* La guarda se escribió para **suspend/resume**, donde el mapeo sigue existiendo; la **retirada en caliente**, donde el mapeo se destruye, nunca estuvo en su alcance. Y en builds de producción `UVM_ASSERT` no evalúa nada. |
| Lo que NO es la causa (descartado por la propia cronología) | **(a) No es la wifi**: el `NMI_INTERRUPT_UNKNOWN` de `iwlwifi` es de `20:48:29`, 7 min 40 s después del Oops, y es lo último que alcanza a escribir una máquina ya rota. **(b) No es el replug** (la trampa de [H27](#h27) y de la memoria del repo): el replug de `20:41:02` es posterior al Oops y no pudo causarlo, solo garantizó que la tarjeta no volviera. **(c) No es el estado de la GPU interna**: su `Xid 154` es consecuencia del mismo evento, no un fallo propio. **(d) No es `nvidia-modeset`**, que es lo que colgaba en H27: aquí la retirada PCI **sí terminó** (`busn_res … is released` a las `20:40:45.791`), y precisamente por eso el mapeo ya no existía cuando UVM lo usó. |
| Relación con los modos de fallo ya catalogados | Falsifica parcialmente el nº 4 del índice (`/dev/nvidia-uvm` close-path, **RESOLVED — benign**). Esa resolución es correcta en lo que midió: n=6 sondas sobre una GPU **presente y sana**, donde `uvm_va_space_destroy` solo toca estado interno. El caso no probado es el último cierre de UVM sobre una GPU **retirada en caliente**, que es otra función (`uvm_va_space_mm_shutdown`, no `va_space_destroy`) y sí toca MMIO. Es además la variante dura de [H2](#h2): allí retirar con descriptores abiertos *cuelga*; aquí *oopsea*. |
| Agravante medido | Entre `20:40:41.679` y el Oops, NVRM escribió **221 060 líneas** en el journal en 8 segundos (`_threadNodeCheckTimeout`, `nvCheckOkFailedNoLog`, `_issueRpcAndWait` en bucle). El coste de ese volcado es parte de por qué la ventana entre el Xid y el cierre del proceso es de segundos y no de milisegundos. |
| Hipótesis | El fallo es de **orden de vida**, no de lógica: `nv_pci_remove` destruye los mapeos de BAR mientras `nvidia_uvm` conserva el `parent_gpu` retenido y con punteros a ellos. Si el camino de cierre de UVM comprobara la presencia del dispositivo antes de tocar el fault buffer —o si la retirada invalidara los punteros de `rm_info` en vez de solo desmapearlos—, el cierre del proceso terminaría sin escribir y el host sobreviviría a la desconexión. |
| Mitigación inmediata, sin parche (la que vale hoy) | **Drenar los procesos CUDA antes de tocar el cable.** `lsof /dev/nvidia-uvm` y cerrarlos; solo entonces desconectar. La regla operativa que ya teníamos cubría el *después* ("tras `Xid 154`, reiniciar, no reconectar") y no cubría el *antes*. |
| Resolution test | Con la caja conectada y sana, lanzar un proceso CUDA trivial que mantenga el contexto abierto, confirmar con `lsof /dev/nvidia-uvm` que lo tiene, y desconectar el cable; después matar el proceso y mirar si aparece el `page fault` en `uvm_hal_turing_disable_replayable_faults`. Todo envuelto en `sudo aorus-egpu-probe run --`, y el veredicto se lee tras reiniciar con `sudo aorus-egpu-postmortem`. **Cuesta un reinicio por repetición**, así que resuelve con n=3 solo si hace falta confirmar PROVEN; el mecanismo ya está leído y el orden inverso (drenar primero) es la prueba barata: si drenando no ocurre nunca, la correlación queda establecida sin provocar más Oops. |
| If supported | El fix es de driver y tiene la forma de las palancas I, J-2, N y O (cortocircuito "GPU perdida" en el camino que toca MMIO): comprobar presencia en `uvm_parent_gpu_replayable_faults_intr_disable` antes de llamar al HAL, y saltarse la escritura con el refcount intacto. Va a `kernel/patches/`, con el coste de rebase que ya arrastra el DKMS. En el lado userspace, un gate de dominio "¿hay alguien con `/dev/nvidia-uvm` abierto?" puede negarse a preparar una desconexión, igual que el gate de enlace se niega con el enlace degradado. |
| If rejected | Si drenando los procesos CUDA la desconexión sigue oopseando en el mismo sitio, el puntero rancio no viene del `va_space` de un proceso sino del propio `parent_gpu` global, y entonces el problema está en la retirada de `nvidia.ko`, no en el cierre de UVM: habría que mirar por qué `nv_pci_remove` no invalida `fault_buffer.rm_info`. |
| Layer | L3 (driver: `nvidia-uvm.ko`). La desconexión en sí y la retirada PCI funcionan correctamente; el fallo está en quién toca el MMIO después. |
